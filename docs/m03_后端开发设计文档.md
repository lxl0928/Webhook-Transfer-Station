# Webhook 中转站后端开发设计

版本：1.1。角色：后端开发工程师。
依据：[需求](m01_需求详细设计文档.md)、[架构](m02_技术架构详细设计文档.md)。可执行的请求参数模型见 `app/schemas.py`，在线规范以 `/docs` 与 `/openapi.json` 为准。

## 1. REST API

管理接口均需 `Authorization: Bearer <token>`，登录和公开健康接口除外。公开源站回调使用 Gitee 密钥校验。

| 方法 | 路径 | 功能 | 成功响应 |
| --- | --- | --- | --- |
| POST | /api/auth/login | JSON 用户名密码登录 | 200 access_token / token_type / user |
| POST | /api/auth/logout | 撤销用户现有 Token | 204 |
| GET | /api/users/me | 当前用户资料（无密钥明文） | 200 |
| PATCH | /api/users/me | 部分更新资料、模型与密码 | 200 |
| GET | /api/webhooks | 分页 / 名称查询 | 200 items / total |
| POST | /api/webhooks | 创建规则 | 201 |
| GET | /api/webhooks/{wid} | 查询单规则 | 200 |
| PUT | /api/webhooks/{wid} | 替换非敏感配置，保留未提供的秘密 | 200 |
| DELETE | /api/webhooks/{wid} | 删除规则，保留历史日志与队列 | 204 |
| POST | /webhooks?wid=… | 多源回调 | Gitee 202；通用/夜莺及重复 delivery 200 |
| GET | /api/webhook-logs | 分页及条件查询 | 200 items / total |
| GET | /api/webhook-logs/{id} | 查询输入输出详情 | 200 |
| POST | /api/webhook-logs/{id}/retries | 为失败记录创建重试请求 | 202 |
| GET | /health/live | 进程存活 | 200 |
| GET | /health/ready | 后端与数据库 | 200 / 503 |
| POST | /api/health/llm | 当前用户真实模型调用检测 | 200 / 503 |

默认分页 `page=1&page_size=20`，最大 100。规则查询 `q` 使用转义后的子串匹配；日志支持 `wid,status,trace_id,start,end`，时间参数使用 ISO8601，建议显式 `Z` 或时区偏移。

错误采用 FastAPI 风格 `{"detail": ...}`，响应 Header 携带 Trace ID。401 为未授权/密码错误，403 为回调仓库不匹配，404 为资源不存在或不属于用户，409 为状态冲突，413 为体积超限，422 为字段校验失败，429 为登录限流，503 为依赖健康异常。未预期异常返回无内部堆栈的 500。

## 2. 请求示例

### 2.1 登录

```json
{"username":"admin","password":"Admin#123."}
```

### 2.2 更新 LLM

```json
{
  "llm_host":"https://api.openai.com/v1",
  "llm_api_key":"<your-api-key>",
```

Host 需包含服务提供方的 API 基础路径，程序只追加 `/chat/completions`。留空 Key 的界面行为为不提交该字段；API 的显式空字符串可清除 Key。

### 2.3 新增规则

```json
{
  "name":"核心服务研发群",
  "source_url":"https://gitee.com/team/service",
  "source_info":{"team":"研发一组"},
  "source_secret":"replace-with-strong-secret",
  "events":["push","pull_request","tag","comment"],
  "source_template":"仓库：{{repository}}\n事件：{{event}}\n{{payload}}",
  "llm_enabled":true,
  "llm_prompt":"用中文概括事件，保留作者、链接和重要变更，控制在500字以内。",
  "target_type":"wecom",
  "target_url":"https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<robot-key>",

```

返回字段包含 `wid,url,source_secret_set,target_url_set,target_secret_set`，不包含密钥明文。PUT 需提供完整非敏感字段；敏感字段为空缺或 null 时保留原值。可选 target_secret 显式 `""` 清除。

## 3. Gitee 回调处理算法（夜莺/通用流程见第 9 节）

1. 通过严格格式的 wid 查询规则，拒绝不存在或停用的规则。
2. 流式读取 JSON，累计超过 1 MiB 立即拒绝；必须为对象。
3. 从 X-Gitee-Token（优先）或 payload.password 取得源站密钥并比较。
4. 校验 repository.html_url / repository.url 与配置一致。
5. 根据 X-Gitee-Event 和 tag ref 归一化事件，判断订阅范围。
6. 递归替换已知凭证键的值为 `[REDACTED]`。
7. 快照规则、当前用户模型配置并整体加密，创建 pending 或 ignored 日志。
8. 数据库提交成功才确认接受（Gitee 202，其他源站 200）；如 `(wid,delivery_id)` 唯一冲突，返回已有日志 ID，不重复创建。

鉴权失败/非法 JSON 等未接受的请求不写业务消息日志，只进入请求状态/耗时日志；防止攻击者通过未授权输入填满消息库。input_payload 是经过凭证脱敏的业务输入，不是原始字节级归档。

## 4. Worker 设计

领取 SQL 逻辑：

```sql
SELECT * FROM tb_webhooks_log
WHERE status = 'pending'
ORDER BY received_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

在同一事务中设为 processing、started_at=UTC now、attempts+1，然后提交。处理时解密快照，构造模板上下文。若启用 LLM，则调用模型并保存结果；否则令 llm_output=源站模板内容。渲染目标模板、校验 UTF-8 消息字节数并构造平台 body，先保存输出，再发出 HTTP。

默认输出飞书 interactive、企业微信 template_card/text_notice、钉钉 actionCard。企业微信卡片正文在本应用限制为 1024 字符，各平台完整卡片保守限制为 20000 UTF-8 字节；超过上限直接 failed，不静默截断正文。签名会增加少量请求体开销，以平台业务错误为准。飞书卡片内使用 at id；企业微信、钉钉在卡片成功后追加原生文本 @ 提醒，部分失败须明确提示卡片已发送。

飞书 payload：`{"msg_type":"text","content":{"text":"..."}}`；企业微信/钉钉：`{"msgtype":"text","text":{"content":"..."}}`。HTTP 200 外，飞书要求 code/StatusCode=0，其他平台要求 errcode=0；缺少业务码不算成功。

飞书签名使用秒级 timestamp 与 `timestamp + "\n" + secret` 作为 HMAC-SHA256 key，对空字节求 HMAC，再 base64；签名字段放 JSON。钉钉使用毫秒 timestamp，对 `timestamp + "\n" + secret` 以 secret 求 HMAC，再 base64；保留原 URL access_token，追加 timestamp/sign 查询参数。

异常分为可安全展示的 DeliveryError 和通用异常类型。不上报含 token URL 的原始 HTTP 异常文本，不存上游任意返回 body，仅存成功响应的 HTTP 状态与业务码；拒绝响应的业务码体现在 error。

## 5. 身份与数据安全实现

- 所有用户资源查询依赖 current_user；不存在与越权统一 404。
- 密码运算通过 asyncio.to_thread，避免长哈希阻塞事件循环；未知账户也验证虚拟 hash，减少用户名枚举时序差异。
- JWT 必须包含 exp/iat/sub/ver，固定 HS256；token_version 与数据库值比较。
- 单进程每地址每分钟默认 10 次登录尝试；nginx 外层再限流。API 不信任任意客户端转发 IP Header。API 限流在默认 nginx 部署下可能按代理地址合并计数，适合本版单管理员；多管理员部署应改为可信代理解析与共享限流。
- HTTP Client 默认不读取环境代理、不跟随重定向；目标地址白名单及 LLM 主机允许列表在保存和外发时都校验。
- 模板只替换白名单变量，不使用任意表达式求值器。
- JSON 凭证递归脱敏只覆盖已知键名，不能自动识别任意业务文本中的秘密。

## 6. Trace 与时间语义

前端每次请求生成 X-Trace-Id，后端验证并透传。回调的 Trace ID 写入日志，worker 对 LLM 与目标平台 HTTP 请求传递同一 ID。重试沿用原消息 Trace ID，配合 attempts 判断尝试次数。

`received_at` 是写入队列时间；`started_at` 是最近一次领取时间；`output_at` 仅成功投递有值；`finished_at` 表示本轮终止，包括失败/忽略；`cost_ms` 是 worker 本轮执行耗时，不含等待队列时间。HTTP 请求另有独立 cost_ms。

## 7. 配置、迁移与开发

必须设置 JWT_SECRET（至少 32 字符）和有效 ENCRYPTION_KEY。通过 `scripts/init_env.py` 生成；丢失加密密钥将无法恢复已存 Key 和队列快照。备份数据库时必须单独安全备份该密钥。

使用 Alembic 初始迁移 `0001` 与兼容升级 `0002`，禁止生产依赖 metadata.create_all。初始化管理员由独立一次性任务执行，已存在用户名不重置密码。新结构修改应新增版本迁移，不改已部署迁移文件。

运行方式与依赖命令见根 README。新增后端模块遵守 Ruff；测试使用 pytest-asyncio、httpx ASGITransport/MockTransport。外部模型与机器人默认全部 mock，测试不能向真实群发送消息或消耗模型费用。

## 9. 新增 API 字段与通用源站算法

```json
{
  "source_type": "nightingale",
  "source_auth": "header",
  "source_token_header": "X-Webhook-Token",
  "source_url": "",
  "events": [],
  "target_mentions": {"all": false, "user_ids": ["ou_member"], "mobiles": []}
}
```

上述字段合并到原创建/更新请求。source_type 为 gitee/nightingale/generic；source_auth 为 header/bearer/query。Gitee 忽略自定义 Header 名称，固定原校验流程。非 Gitee 按配置读取 Header、Authorization Bearer 或查询参数 token，再解析事件；不读取 JSON password 作为认证。解析流程支持 JSON（夜莺/通用可数组/标量，拒绝 null）、通用 text/plain 和 application/x-www-form-urlencoded。源站地址在非 Gitee 规则中可空，事件列表空表示全部；通用回调缺失可用事件名时归为 webhook。

夜莺单条按 is_recovered 判断 alert/recovery，数组或 events 数组归 alert_batch；X-Webhook-Event 可显式覆盖。X-Webhook-Delivery 用于幂等，仅存在时去重；HTTP 200 表示接受入队，不表示已送达。原 Gitee 回调继续返回 202。OpenAPI 已声明支持的 Content-Type、URL token 参数与 200/202 响应。

模板新增 source_url/source_type/source_info 与安全点路径，如 payload.error.message、payload.events.0.rule_name、source_info.team；只遍历 JSON dict/list，不进行 Python 属性访问；缺失路径为空。

目标人员组装：飞书 text 附加 `<at user_id="ou_...">成员</at>`，@所有人使用 all；企业微信在 text 添加 mentioned_list / mentioned_mobile_list；钉钉顶层添加 at.atUserIds / at.atMobiles / at.isAtAll，并在 text.content 补充对应 @ 标记。先加入提醒元素再计算字节上限，最后仍走已有签名、HTTP 与业务码校验。不要把三平台的用户 ID 混用。

测试新增三平台提醒矩阵、飞书标签注入与长度、无效名单、三种回调鉴权、通用内容类型、夜莺事件识别、嵌套模板、通用事件筛选与去重、名单快照冻结。真实平台人员提醒效果需以用户群配置联调验收。

## 扩展：源站回调鉴权开关

每条规则新增 source_auth_enabled，默认 true，迁移 0004 保持已有规则鉴权开启。false 时不要求源站回调密钥，依靠有效 wid 定位规则；其并不证明调用方身份。其他消息校验、管理接口 JWT、目标机器人签名不变。关闭保留旧密钥，开启必须配置有效密钥。规则表单与聊天工具均支持此字段。
